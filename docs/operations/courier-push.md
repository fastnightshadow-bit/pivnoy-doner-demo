# Фоновые уведомления курьера

## Что делает система

- Уведомление создаётся только для новой оплаченной доставки.
- Повторный webhook ЮKassa не создаёт второе уведомление.
- Самовывоз и неоплаченный заказ уведомление курьеру не создают.
- В push нет телефона клиента, PIN-кода или платёжных данных. Полные данные курьер получает только после входа в приложение.
- Открытая страница продолжает обновляться через SSE; фоновый push нужен для закрытого приложения.

## Переменные окружения

В `deploy/.env.stage` и `deploy/.env` используются:

```text
VAPID_PUBLIC_KEY=
VAPID_PRIVATE_KEY=
VAPID_SUBJECT=mailto:piv.don@ya.ru
PUSH_POLL_MS=2000
```

Для stage и production обязательны разные пары ключей. Приватный ключ нельзя добавлять в Git, HTML, логи или переписку.

## Создание и ротация VAPID

1. Создать отдельную пару для stage и отдельную пару для production командой `npx web-push generate-vapid-keys --json` в защищённом терминале.
2. Сразу записать значения в соответствующий серверный `.env`; не сохранять вывод в репозитории.
3. Пересоздать только API-контейнер.
4. После смены ключей ранее установленные PWA должны снова нажать «Включить уведомления». Старые подписки со временем будут деактивированы.

Пример перезапуска stage из `/opt/pivdoner/deploy`:

```bash
docker compose --env-file .env.stage -f docker-compose.stage.yml up -d --build api
```

Для production используется `.env` и `docker-compose.production.yml`.

## Проверка на телефоне

1. Открыть реальный адрес курьера и войти.
2. Нажать «Включить уведомления» и разрешить их в браузере.
3. Убедиться, что карточка показывает «Уведомления включены».
4. Полностью закрыть PWA.
5. Создать и оплатить тестовую доставку.
6. Должно прийти одно уведомление; по нажатию открывается реальная страница курьера.
7. Отдельно проверить, что самовывоз уведомление не создаёт.

Android: поддерживаются актуальные Chrome/Chromium-браузеры. На iPhone нужен iOS 16.4 или новее, а сайт должен быть добавлен на экран «Домой» как PWA. Режим инкогнито и запрет уведомлений на уровне системы могут блокировать push.

## Диагностика

Проверить состояние очереди без вывода содержимого payload:

```bash
docker exec -it pivdoner-stage-db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "select status, count(*) from push_jobs group by status order by status;"'
```

Для production заменить контейнер на `pivdoner-db`.

Последние задания:

```sql
select id, status, attempts, available_at, sent_at, last_error
from push_jobs
order by id desc
limit 20;
```

Подписки без endpoint и криптографических ключей в выводе:

```sql
select active, count(*), max(last_success_at) as last_success
from push_subscriptions
group by active;
```

Значения состояний:

- `pending` — ожидает отправки или повторной попытки;
- `sending` — взято обработчиком; зависшее более двух минут будет подобрано снова;
- `sent` — обработано;
- `dead` — исчерпаны попытки, требуется проверить `last_error` и настройки.

Ошибки 404/410 от push-сервиса автоматически отключают устаревшую подписку. Временные ошибки повторяются с ограниченной задержкой и не блокируют оплату заказа.

## Частые проблемы

- «Уведомления запрещены»: разрешить их в настройках браузера/системы, затем снова открыть приложение.
- После ротации ключа уведомления не приходят: нажать «Отключить», затем «Включить».
- Заказ виден на экране, но push не пришёл: проверить системное разрешение, наличие активной подписки и очередь `push_jobs`.
- Push пришёл дважды: проверить, что один и тот же заказ имеет только один `event_key`; повторный webhook должен упираться в уникальное ограничение.

## Безопасность

- Не выводить `VAPID_PRIVATE_KEY`, endpoint, `p256dh` и `auth` в поддержку или общие логи.
- Доступ к API подписок разрешён только авторизованным курьеру и владельцу.
- При выходе текущая браузерная подписка удаляется с сервера и из браузера.
- При компрометации приватного ключа немедленно создать новую пару, заменить её в нужном окружении и пересоздать API.
