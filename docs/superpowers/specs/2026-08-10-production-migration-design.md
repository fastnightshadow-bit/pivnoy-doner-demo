# Production Migration Design

## Цель

Перенести «Пивной Донер» с демонстрационной версии GitHub Pages на сервер владельца `194.87.147.92`, подключить домен `pivdoner.ru` и подготовить единую рабочую систему, которая после проверки заменит существующий Telegram-бот.

## Принятое решение

Используется безопасное параллельное развёртывание. Существующие контейнеры, сайт `pivnoy-doner.digital`, Telegram-бот и их данные не изменяются во время сборки и проверки новой системы. Новая система размещается отдельно в `/opt/pivdoner` и подключается к уже работающему Caddy только после создания резервных копий.

Telegram-бот отключается только после полного теста заказа и успешного первого рабочего заказа через новый сайт. Старый стек сохраняется 14 дней для быстрого возврата.

## Домены

- `pivdoner.ru` и `www.pivdoner.ru` — клиентский сайт.
- `kitchen.pivdoner.ru` — рабочее PWA кухни.
- `courier.pivdoner.ru` — мобильное PWA курьера.
- `owner.pivdoner.ru` — панель владельца, когда она будет реализована.

Все домены получают HTTPS через существующий контейнер Caddy. Запросы `/api/*` передаются серверному API, остальные запросы — веб-контейнеру.

## Архитектура

Новая система запускается отдельным Docker Compose-проектом:

- `pivdoner-web` — статические клиентские, кухонные и курьерские PWA.
- `pivdoner-api` — Node.js API, серверная проверка цен, заказов, ролей и статусов.
- `pivdoner-db` — PostgreSQL с постоянным Docker volume.
- существующий `caddy` — HTTPS и маршрутизация, без замены контейнера.

Новые контейнеры используют собственную внутреннюю сеть. Только `web` и `api` подключаются к внешней сети `pivnoy_doner_caddy`. База данных недоступна из интернета.

## Данные

PostgreSQL хранит:

- каталог и доступность блюд;
- заказы и позиции с выбранными параметрами;
- стоимость, доставку, скидки и оплату;
- адрес, этаж, квартиру, домофон и телефон;
- текущий статус и полную историю статусов;
- роли кухни, курьера и владельца;
- отзывы только завершённых заказов;
- настройки приёма заказов и стоп-лист;
- события для надёжной доставки уведомлений.

Цена всегда пересчитывается сервером. Значение, присланное браузером, не считается доверенным.

## Поток заказа

1. Клиент собирает корзину и отправляет её API.
2. API проверяет каталог, добавки, соусы, часы работы, минимальную сумму и стоимость доставки.
3. До подключения ЮKassa заказ создаётся в тестовом режиме без реального списания.
4. После подключения ЮKassa API создаёт платёж и ожидает подтверждённый webhook.
5. Только подтверждённый оплаченный заказ появляется на кухне.
6. Кухня меняет статусы по разрешённой последовательности.
7. Клиент и курьер получают обновления автоматически через Server-Sent Events; действия отправляются обычными REST-запросами.
8. При потере связи интерфейс не показывает ложный успех и предлагает повторить отправку.

## Расчёт времени

Базовое время одной шавермы — 6–7 минут. На кухне постоянно работают два повара, каждый может одновременно готовить до трёх шаверм. Сервер рассчитывает ориентир по числу активных порций, текущему этапу и ближайшему свободному слоту поваров. Окончательное время показывается как диапазон, а не как точная гарантия.

## Доступ и безопасность

- Демо-PIN `0000` не используется в производстве.
- PIN кухни, владельца и курьера хранится только как Argon2id-хеш.
- Авторизация выдаёт защищённую `HttpOnly`, `Secure`, `SameSite` cookie.
- У кухни один общий рабочий доступ, как подтвердил владелец.
- Владелец имеет полный доступ; кухня и продавец управляют заказами, стоп-листом и приёмом заказов; курьер видит только назначенные доставки.
- Секреты ЮKassa, ключи сессий и пароли базы хранятся только в серверном `.env` с правами `600`.
- API ограничивает частоту входов, создания заказов и повторных запросов оплаты.
- В логи не записываются PIN, платёжные секреты и полные персональные данные.

## ЮKassa

Платёжный модуль создаётся с тестовым адаптером. Для рабочего включения владелец позднее передаёт `shopId` и секретный ключ безопасным способом; они не попадают в Git или переписку. Webhook проверяется сервером, а повторный webhook не создаёт второй заказ или повторное действие.

## Резервное копирование и возврат

До первого изменения сохраняются:

- `/root/pivnoy_doner`;
- `/root/govno1`;
- Caddyfile;
- список и конфигурация контейнеров;
- архивы Docker volumes существующих баз.

Для новой базы создаётся ежедневный дамп с хранением семи последних копий. Возврат выполняется восстановлением прежнего Caddyfile и перезагрузкой только Caddy; старые контейнеры до конца периода возврата не удаляются.

## Последовательность запуска

1. Проверить состояние сервера и создать резервные копии.
2. Подготовить production-код, тесты, Dockerfile и Compose локально.
3. Развернуть систему параллельно на тестовом адресе.
4. Проверить клиента, кухню и курьера на телефоне и планшете.
5. Провести полный тестовый заказ без реального платежа.
6. Настроить DNS `pivdoner.ru` и поддоменов на `194.87.147.92`.
7. Подключить тестовый, затем рабочий режим ЮKassa.
8. Провести один контролируемый рабочий заказ.
9. Выключить Telegram-бот и оставить старый стек остановленным, но сохранённым на 14 дней.

## Проверка нагрузки

Перед переключением выполняется тест минимум на 100 одновременных посетителей и пакет одновременных оформлений. Проверяются время ответа API, отсутствие дублирующихся заказов, корректность блокировки повторных платежей, обновления кухни и использование памяти. Развёртывание не считается готовым, если сервер отвечает ошибками или теряет события.

## Критерии готовности

- Все четыре адреса открываются по HTTPS.
- Заказ сохраняется в базе и не теряется после перезапуска контейнера.
- Кухня получает заказ без перезагрузки страницы.
- Нелогичные переходы статусов отклоняются сервером.
- Курьер видит время готовности, адрес, этаж, квартиру, домофон и телефон.
- Клиент автоматически получает изменения статуса.
- Повторное нажатие и повторный webhook не создают дубликат.
- При отказе нового стека прежний сайт можно вернуть без потери его данных.

## Что требуется от Ильи

До тестового размещения ничего. Перед открытием домена потребуется настроить DNS-записи REG.RU. Перед рабочей оплатой потребуются реквизиты ЮKassa владельца, переданные вне Git и публичной переписки.
